## 审查执行摘要（Executive Summary）

在完成 CONTROL-RESET-01 工程治理收口并同步 NAS 权威仓后，本审查对当前系统的**业务能力（M1~M6）**、**系统底座（S1~S4）**、**认知引擎（Phase 2A Cognition）**及**盘股知识资产卡（KA-01~15）**进行了无死角穿透式对账。

### 核心审查发现

1. **工程控制与核心账本底座极其扎实（Grade A）**：
   - **M3（实盘交易不可变账本）**与 **S3（HITL 人机隔离）**实现度最高，具有会计级红字冲正、成本核算、超卖拦截与 7 组对抗测试，达成全链路闭环；
   - **S1（工程底座）**经过治理后已具备测试沙箱硬隔离、Alembic 空库可复现迁移与标准绝对路径。
2. **认知引擎存在巨大的“沙箱已全通，生产未接入”断层（Grade A Contract / Grade D Runtime）**：
   - **Phase 2A 核心认知资产**（JCS规范化、防雪崩哈希链、收窄AST解释器、三态事后证伪、确定性重放、五维Diff）在 `backend/app/cognition/` 拥有 **4,800+ 行严密代码实现**，并通过了 **148 项自动化测试与 AC-01~13 硬指标**；
   - **但物理现实是**：系统定时任务调度器（`scheduler.py`）与核心生产链路中，**对 Phase 2A 认知引擎的调用量严格为 0**！所有测试均在沙箱与内存 Mock 中运行，生产数据库中 `cognition_record` 行数物理为 0。
3. **盘股 15 张知识资产卡呈现“1 个实现、1 个空壳、13 个纯纸面概念”的极端分化**：
   - **唯一有代码支撑**：KA-12（会计级红字冲正，位于 `trading.py`）；
   - **仅有空壳契约**：KA-10（三层候选池，仅有 Pydantic 模型与空表，业务逻辑 0 行）；
   - **其余 13 张卡（KA-01~09, KA-11, KA-13~15）在代码库中完全不存在（支持代码 = 0 行）**，属于纯数学推演、论文设计或交易心得，且严重缺乏底层数据支撑（如缺行业分类版本、成分股历史日频、融资融券与海外高频宏观源）。
4. **策略引擎处于绝对断层状态（Grade F）**：
   - **M6（策略与选股）**仅有 36 行 CRUD 空壳代码，无任何筛选算法、排序打分或选股执行能力，必须维持**绝对封存**。

## 第三部分：Cognition Layer（Phase 2A）真实接入度穿透审计

这是本次审查最核心的“现实照妖镜”。前期文档产生了大量的“Phase 2A Step 1~6 实施完成报告”与“契约冻结单”，必须严格区分**代码与契约的存在** vs **生产运行时的接入**。

### 1. 代码层面存在的事实（Physical Code Assets）
在 `backend/app/cognition/` 目录下，物理存在 24 个模块文件：
- **规范化与密码学**：`jcs.py`（RFC 8785 JCS 字段保序与高精度浮点转换）、`hash_chain.py`（抗雪崩哈希链计算与前向校验）；
- **假说与收窄 AST**：`evaluator.py`（强制 AST 白名单，阻断 `__import__`、`eval`、系统内省攻击）、`falsification.py`（假说失效红线判断，强校验 `CONFIRMED`/`FALSIFIED`/`INCONCLUSIVE`，严禁偷填 0）；
- **适配器矩阵**：`adapters/m1_adapter.py`、`m2_adapter.py`、`m4_adapter.py`、`m5_adapter.py`、`s4_adapter.py`（将各模块输出转化为不可变观察快照 `ObservationSnapshot`）；
- **时钟与重放**：`clock.py`（严格四维时间语义：有效推演时点、实际物理时钟、时钟冻结防穿越）、`replay/runner.py`（确定性重放引擎）。

### 2. 运行时调用的真实断层（Runtime Disconnect Reality）
经过对业务调度主链路（`backend/app/tasks/scheduler.py`）与系统主入口（`backend/app/main.py`）的全局文本检索：

| 检查项 | 事实结果 | 审查结论 |
| :--- | :---: | :--- |
| **`scheduler.py` 是否调用认知引擎** | **0 处调用** | 调度器仅调用 M1、M2、M4、M5 的生成服务，未调用任何 Cognition 构建或推演。 |
| **M1/M2/M4/M5 内部是否触发 CognitionRecord 生成** | **0 处触发** | 业务服务仅写入自身业务表，未触发 `app.cognition.input.pipeline`。 |
| **生产数据库中 `cognition_record` 行数** | **0 行** | 物理数据库中该表结构完备，WORM 触发器存在，但生产数据记录为 0。 |
| **生产数据库中 `cognition_chain_state` 行数** | **仅 1 行** | 仅包含迁移时初始化的 Genesis 创世锚点行（Sequence 0, Hash 000...）。 |
| **外部大模型 API 调用量** | **0 次** | 零 API Key，零外部请求，未发生任何大模型推演。 |

### 3. 架构现实定性
> **Phase 2A 认知引擎当前的真实定位是：【高标准、已验证的静态契约与沙箱演练固件（Verified Contract Sandbox）】。**  
> 它的代码质量极高、测试覆盖极其严密，但它**尚未接入生产生命周期的管道**。任何将其表述为“已在实盘运行”的说法都是虚假的。

## 第五部分：P0 增强准入红线与硬门禁裁决（P0 Admission Hard Gates）

针对此前草案中提出的“P0 增强包（KA-01/03/05/06）”，基于本轮审计的客观现实，正式下达**架构准入门禁裁决**：

### 1. 绝对禁止进入 P0 的负面清单（Hard Quarantined）
- ❌ **M6（策略与选股引擎）**：严禁解封，继续封存。在基础数据与感知层未稳定前，绝不允许开发自动化策略。
- ❌ **KA-02（板块透支年限）与 KA-08（五源宏观预警）**：维持 `Validate First` 决议，缺乏物理数据源支撑，严禁作为生产功能开发。
- ❌ **KA-11、KA-13、KA-14**：缺乏 Tick 级数据与季报资产库，严禁借 P0 名义引入。
- ❌ **任何生产环境调用未经审计的 LLM API 行为**：严禁放开。

### 2. 候选 P0 项目的“四大前置硬门禁”（The 4 Hard Gates for P0 Admission）
任何候选功能在**编写第一行生产代码之前**，必须满足以下硬门禁，否则一票否决：

