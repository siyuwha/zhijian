## 二、T02-01：模拟股票 T+1 与风控成交一致性

### 证据与目标

今日流水 ID 13、14 买入，ID 15、16 当日全部卖出；检查记录确认该模拟成交不符合适用 A 股股票 T+1。本地自动风控直接提交持仓数量卖出是定位线索，尚未直接核验容器源码。目标为所有模拟股票卖出入口执行同一可卖规则，并准确记录实际成交。

### 实施范围与措施

- 核对 simulation 服务、自动执行器、模拟交易 API、持仓及流水模型和既有测试；按交易日及成交顺序核算昨日可卖仓与今日新增仓。必要时调整模型，但先给出数据迁移和回滚方案。
- 在共享成交入口约束手动与自动卖出，不能只在页面或自动策略中拦截。对不在本次范围的 T+0 品种不套用股票规则；未知品种不得猜测支持。
- 风控触发、不可卖拒绝、部分可卖和实际成交分别记录。手动超可卖请求明确拒绝且不部分写入；自动风控仅提交可卖数量，不可卖余量保留持仓并记录原因。
- 持仓周期与可卖数量分开计算，按交易日历处理尾盘到期信号；日历不可用时明确阻止依赖该判断的操作。
- 在持仓被成交函数更新前保存实际成交数量，核对事件、现金、持仓和流水。防止并发卖出重复占用可卖数量。
- 列出手续费、涨跌停、流动性等现有建模限制，本轮不扩展完整撮合引擎，不改写历史违规流水或收益。

### 验收样例

| 场景 | 预期 |
| --- | --- |
| 当日首次买入 1000 股，当日手动或风控要求卖出 | 成交为 0，明确 T+1 原因，资金、持仓、流水不变 |
| 昨日持仓 600 股，今日买入 400 股，手动要求卖 1000 股 | 拒绝；不产生部分写入 |
| 同一混合持仓触发自动全平 | 仅成交可卖的 600 股，保留今日 400 股；事件数量为 600 |
| 昨日可卖 600 股，先卖 200 股，再卖 400 股 | 两次通过，再次卖出被拒绝 |
| 两个并发请求争用同一可卖仓 | 累计成交不超过可卖数量，无负持仓或重复扣减 |
| 周五买入、周末及节假日、下一交易日 | 非交易日不自动成交；下一适用交易日才转为可卖 |
| 今日买入触发尾盘持仓到期信号 | 记录触发及不可卖原因，不当日强平 |

验证使用隔离账户、可控时钟及交易日历，覆盖 API 与自动入口，复跑模拟统计专项。历史 ID 13—16 仅做只读对账和影响说明，不在生产补成交。

## 三、T03-01：质量日志事务与风控失败隔离

### 证据与目标

今日 09:44:50 记录 data_quality_log.id 唯一约束冲突及后续未回滚会话；最新 500 条任务记录中另有 79 次今日监控成功。不能据此推算全天故障率或认定主键生成根因。

### 实施范围与措施

- 核对 data/quality.py、质量日志模型及数据库定义、会话依赖、monitor 服务与 scheduler 的调用顺序。通过隔离库复现主键冲突或提供经验证的根因证据，排查显式 ID、表结构、连接及并发写入；不预设 SQLite 序列损坏。
- 明确日志写入事务的所有权。失败后回滚正确会话，必要时用独立短事务，避免回滚业务事务；禁止仅吞异常、删日志或直接重置生产主键。
- 监控采集、质量记录和风控具有分别可观察的结果。非关键日志失败时风控仍有独立执行机会；必要行情缺失时风控明确跳过，不使用无效行情成交。

### 验收样例

- 注入唯一约束冲突：本轮记录质量写入失败；后续写入可以成功，无失效会话连锁错误。
- 注入快照持久化失败但保留有效行情：风控仍获得一次执行机会，监控和风控结果分别记录。
- 行情无效且日志失败：不伪造成交，明确记录两个失败原因。
- 并发写日志：无重复主键；独立日志事务失败不提交或撤销模拟成交事务。

交付故障注入证据和事务边界说明。后续部署观察覆盖至少一个完整交易日，按任务类型列出全部可取得记录及时间范围；不能用最近 500 条代替全天。

### 实施范围与措施

- 比较原始字段后再确定最小修复，不以修改某个数字强行对齐两份快照。

### 验收样例

- 同时点沪市 6000、深市 9000、创业板 3000、科创50 800 亿元：两市总额为 15000，不是 18800。
- 同一金额的三种单位输入归一后相同；有效零值与缺失分别处理。
- 一侧缺失、过期或不同交易日：不返回无质量说明的完整合计。
- 对今日差异形成字段级对账；无法取得当时原始数据时保留“历史原因未确定”，以固定样例证明算法正确。

## 五、T10-01：行情降级定位与质量传递

### 证据与目标

最新 500 条质量记录中，今日板块 DEGRADED 95 条，分时 DEGRADED 49 条、UNAVAILABLE 31 条，包含断连、熔断和过期缓存。该样本不是全天统计；复盘 FULL 不能证明所有能力完整。

### 实施范围与措施

- 按能力、来源、时间和原因归类，不将板块异常归因于未必提供该能力的 TDX。核查连接、超时、熔断恢复、缓存新鲜度和备用源实际能力。
- 只修复有证据的失效环节，复用现有切换机制；不新增供应商或扩大为行情系统重构。
- 让消费者识别来源、数据日期、新鲜度及降级原因。FULL 保留其既有定义并说明能力边界，不能以单一汇总标记掩盖关键数据缺失。
- 无可用实时数据时展示缺失或标记缓存，不伪造分时，不把过期值用于要求实时行情的自动成交。

### 验收样例

- 主源断连、备用源成功：输出注明实际备用来源及有效时间，状态按既有定义判定。
- 双源不可用且缓存过期：明确不可用，不伪装实时成功；页面不中断。
- 分时不可用、复盘其他能力完整：分别显示各自质量，不能以 FULL 推断分时可用。
- 主源恢复：在既有恢复条件满足后恢复取数，无无限重试或频繁切源；不同交易日缓存不串用。

先做隔离故障注入；生产观察需记录完整窗口、分母和能力分布，不要求所有外部数据永不降级。涉及展示时只调整承载质量提示的必要组件。

### 证据与措施

### 验收样例
