### 三、 关键告警容量与零静默丢弃证明 (GATE-3B1-09)

为消除内存缓冲区与死信队列在极端工况下的丢弃盲区，`AlertRingBuffer` 与 `AlertDeadLetterQueue` 新增了结构化度量指标接口 `get_metrics()`，并实施了严苛的极端满载破坏性验证：

1. **CRITICAL 告警突破配额场景**：
   - 设定配额为 5，允许注入 10 个 CRITICAL 告警。证明在缓冲区未满时，配额并不成为限制容量的硬天花板，系统完全包容。
2. **混合优先级满载淘汰场景**：
   - 当缓冲区达到 20 条满载（10 CRITICAL + 10 INFO）时，新进入的 CRITICAL 告警优先淘汰最旧的 INFO 告警；
   - 既有的 10 个 CRITICAL 告警 100% 获得倾斜保护（`critical_protected_drops == 0`）。
3. **全关键告警 100% 满载场景**：
   - 当缓冲区 20 个槽位全部被 CRITICAL 告警占满时，后续注入的 5 个 CRITICAL 告警通过显式淘汰最旧的关键告警腾出空间；
   - 淘汰行为被显式记录在 `critical_protected_drops` 计数器中，`total_overflow_drops == non_critical_drops + critical_protected_drops`，数学恒等式成立。
4. **死信队列 (DLQ) 满载丢弃场景**：
   - DLQ 设定容量为 10，连续注入 15 个毒丸载荷；
   - DLQ 保持容量 10，超出容量的 5 个载荷通过 `total_dropped_count` 显式计数，杜绝无感丢失。

### 四、 密码学信任边界与日志截断防御证明 (GATE-3B1-10)

针对最高董事会关于 HMAC 密钥与 Merkle 链可信锚点的审查要求，正式确立以下信任边界标准：

#### 1. HMAC 签名密钥全生命周期与轮转机制
- **密钥定义与注入**：支持通过环境变量 `ALERT_BUS_SECRET_KEY` 注入生产级安全私钥；在开发/测试阶段具备安全回退默认密钥；
- **签名责任划分**：由事件生成引擎（`AlertEvaluator`）在出站瞬间基于 JCS 规范内容哈希计算 HMAC-SHA256 签名；消费端（WebSocket 网关 / UI 订阅者）承担验签责任；
- **密钥轮转验证**：过期或非法密钥验签立即返回 `False`，事件不予广播并重定向至死信队列。

#### 2. Merkle 审计日志防篡改与尾部截断防御
- **创世可信锚点**：首行绑定全零 64 位字符创世哈希（`0`*64）；
- **外部闭环锚点**：每日收盘时，审计日志最后一行的 `line_hash` 与总行数被抽取并签名固化于法定基线凭证文件（如 `audit_phase3b1_alert_bus_evidence.json`）中；
- **截断攻击捕获**：`AlertAuditLogger.verify_audit_log_integrity(log_path, expected_closing_hash, expected_line_count)` 在比对外部锚点时，若日志被恶意删除尾部行，即使内部哈希链未断，亦会因行数或闭环哈希失配而 100% 阻断报错（`Log truncation detected`）。

### 五、 DOC-96 时间契约与未来时戳/时钟漂移加固 (GATE-3B1-11)

针对最高董事会对采样时间、请求时间与求值时间的语义隔离要求，完成了双向时间偏离防御测试：

1. **未来时戳与负数据年龄防御**：
   - 当客户端本地时钟滞后或数据切片时间超前于请求时间（$T_{observed} > T_{requested}$）时，物理数据年龄计算实施下限钳位保护：$\text{Data Age} = \max(0.0, T_{requested} - T_{observed}) = 0.0\text{s}$；
   - 引擎在事件载荷的 `detail_facts` 中显式打标 `"is_future_skew": True` 及实际负偏离秒数 `"raw_data_age_seconds": -300.0`，确保时钟异常完全可溯源。
2. **确定性历史回放时钟隔离**：
   - 离线回放时，请求时间 $T_{requested}$ 支持显式注入历史时钟，数据年龄严格基于注入时钟计算，杜绝受当前宿主机物理时钟干扰。

## 第二部分：Phase 3B.2 安全分发通道与只读 WebSocket 受控实施设计

### 一、 架构定位与物理边界

Phase 3B.2 的核心使命是构建**盘中告警事件向客户端驾驶舱的安全广播分发机制**，主要承载以下只读通信端点：
1. **只读 WebSocket 通道**：`GET /api/v1/canonical/ws/alerts`
2. **只读 SSE 降级通道**：`GET /api/v1/canonical/stream/alerts`

```
                                  【安全防护边界 (Security Perimeter)】
                                                    │
┌───────────────────────┐                           │   ┌────────────────────────────────┐
│   Phase 3B.1          │                           │   │  客户端驾驶舱 (Cockpit UI)     │
│   纯内存告警总线核心  │                           │   └──────────────▲─────────────────┘
│   (RingBuffer / DLQ)  │                           │                  │ (Read-Only Push)
└──────────┬────────────┘                           │   ┌──────────────┴─────────────────┐
           │ (Internal In-Memory Push)              │   │ WebSocket / SSE 广播分发通道   │
           ▼                                        │   │ (Drop Inbound / Backpressure)  │
┌───────────────────────┐                           │   └──────────────▲─────────────────┘
│  AlertBroadcastHub    ├───────────────────────────┼──────────────────┘
│  - 只读订阅管理器     │                           │
│  - 慢消费者背压队列   │                           │   【服务端物理拔线 (Physical Rejection)】
│  - 客户端握手只读认证 │                           │   客户端入站任何操作消息：
└───────────────────────┘                           │   → 立即丢弃 / 抛出 1008 Policy Violation
                                                    │   → 零数据库直连 / 零交易指令触发
```

### 二、 威胁模型与服务端入站丢弃物理加固

| 威胁场景 (Threat Vector) | 攻击手法描述 | 服务端物理防御措施 |
| :--- | :--- | :--- |
| **T1: 客户端入站操作注入** | 恶意客户端通过 WebSocket 尝试向服务端上行注入下单、撤单或仓位调整指令 | **物理拔线 (Drop Inbound)**：服务端在 WebSocket 连接协议层实现单向流，当 `receive_text()` / `receive_json()` 监听到任何非心跳 (Ping) 的有效载荷时，**立即无条件丢弃并记录安全告警，或以 Code 1008 (Policy Violation) 强制断开连接**。服务端物理执行路径中不存在任何可解析入站交易业务指令的 Handler。 |
| **T2: 慢消费者与惊群阻塞** | 客户端卡顿或恶意网络降速，导致服务端发送队列无界膨胀，耗尽内存 | **有界背压队列与优雅丢弃**：为每个连接设立有界发送队列（如 100 条）。当队列溢出时，优先淘汰最旧的 INFO/WARNING 消息；严重滞后客户端触发主动断链释放资源。 |
| **T3: 仿冒连接与未授权窃听** | 恶意第三方在公网尝试连接告警通道获取战报内参 | **Token 鉴权与只读订阅隔离**：连接握手时核验 Token，限制仅能监听当前交易日的公开告警通道，无任何管理提权可能。 |
| **T4: 乱序重放与伪造事件** | 攻击者在传输链路上注入伪造告警事件 | **事件双重签名硬校验**：广播给客户端的所有事件均携带 Phase 3B.1 的 JCS 内容哈希与源端 HMAC 签名，客户端和网关双重验签防伪。 |
